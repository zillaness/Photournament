# Probe 01 — Chromium capability matrix: file:// vs http://localhost

Generated from the probe run on 2026-07-28. Chromium 141.0.7390.37 (Playwright bundle),
Linux x86_64, 4 vCPU. Every row was executed, not assumed.

## Headline

> A plain double-clicked file:// HTML page gets everything Photournament needs — IndexedDB (Blobs, Files, ImageBitmaps) fully works and survives a browser restart, and showDirectoryPicker actually opens the native dialog on a file:// origin — but nothing may be loaded by URL: fetch, module scripts, and relative-URL Workers are all CORS-blocked, so the app must be one self-contained HTML file whose workers are spawned from blob URLs and pull libheif in via importScripts().

## Architectural implications

- Ship as ONE self-contained HTML file. No <script type="module" src>, no relative-URL Worker, no fetch of any sibling asset — all three are CORS-blocked from origin 'null'. Classic <script src="./x.js"> is the only URL-based loading that survives, so the PRD §8 'asset folder if needed' is viable ONLY for classic scripts.
- Every Web Worker must be constructed from a blob URL (or a data URL). Build worker source as a string in the main bundle, URL.createObjectURL(new Blob([src])), then spawn. Module workers are out unless created from a data URL.
- Load libheif inside the worker via importScripts() of an ABSOLUTE file:// URL resolved from location.href, using the base64-inlined libheif-wasm/libheif-bundle.js. Do not fetch it from the page (blocked) and do not module-import it (blocked). The split build with a separate .wasm is unusable on file://.
- IndexedDB is safe to carry the entire PRD 7.10 persistence story — decisions, tree allocation, labels, thumbnail/preview/sidecar Blob caches. It survives full browser restarts on file:// and stored a 40MB Blob without complaint at ~175 MB/s.
- Namespace the IndexedDB database explicitly (e.g. 'photournament/v1'). Every file:// page in the profile shares ONE origin bucket named file__0 — there is no per-file isolation, the quota is shared with every other local HTML tool, and indexedDB.databases() will list unrelated tools' databases.
- Treat the cache as evictable. storage.persist() returned false even on http://localhost in a fresh profile, so every cached derivative (thumbnail, 1600px preview, HEIC sidecar, phash) must be re-derivable from originals, and resume must restore decisions even when the cache is gone.
- Handle showDirectoryPicker's AbortError as an ordinary no-op, not an error state — user cancellation is the common path. Only SecurityError means 'this origin cannot do this'. Require a real user gesture on the call.
- Do not use OPFS as the file:// storage fallback. It is the single storage API file:// actually loses (SecurityError), while IndexedDB is unaffected.
- Perceptual hashing (§7.7) is viable on file://: canvas is not tainted by Blob-sourced images, getImageData returns real pixels, and the whole decode-to-pixels path runs inside a blob worker.
- Report cache size from navigator.storage.estimate().usageDetails.indexedDB rather than assumptions — quota tracks free disk (0.93GB to 162GB observed across mounts) and file:// is not penalised.
- Do not require, document, or silently depend on --allow-file-access-from-files. Users will not set it, and it is a browser-wide security downgrade. Design so the unflagged file:// column is the only one that matters.

## Not verified

- A REAL OS drag-and-drop of a folder — the PRD §8 primary entry point. DataTransferItem.getAsFileSystemHandle is present with arity 0 on both origins, but Playwright cannot synthesise a native OS drag; a synthetic DataTransfer returns null from it on file:// AND on localhost, so that null says nothing about the real path. Needs a manual human test.
- A PICKER-DERIVED FileSystemDirectoryHandle persisted across a browser restart. The restart test used an OPFS root handle as a stand-in (it survived with queryPermission -> 'granted' and readable entries()). A real picker handle is expected to return 'prompt' and need requestPermission() inside a gesture on resume; that re-grant flow was not exercised because no picker handle is obtainable headlessly.
- Actual HEIC decoding. Only that HeifDecoder constructs and its decode codepath runs cleanly (fed deliberate garbage, returned 0 images). No real .heic file was available, so decode correctness, per-image speed, and memory behaviour at the PRD's ~500-photo volume are untested. That is Probe/Phase 1's job.
- Writing to disk via FileSystemWritableFileStream. createWritable is present on FileSystemFileHandle, and OPFS writes worked, but no write through a picker-derived handle into the user's source tree (sidecars, _finalists_* folders, collision handling) was performed.
- Screenshot of the open native folder dialog. The bundled ffmpeg (/opt/pw-browsers/ffmpeg-1011) is compiled WITHOUT x11grab, so run-picker-screenshot.mjs produces no PNG. The pending-promise state is the evidence instead, which is stronger anyway (API state, not pixels).
- Real Chrome / Edge / Brave release channels, and non-Linux platforms. All runs used Playwright's bundled Chromium 141.0.7390.37 on Linux x86_64 (both headless_shell and the full chromium channel). macOS and Windows file:// behaviour was not tested, and one flag result already proved build-dependent (fetch under --allow-file-access-from-files works in full Chromium but not headless_shell), so cross-build assumptions are demonstrably risky.
- storage.persist() under genuine user engagement. It returned false everywhere here, but a fresh headless profile has no engagement score. Whether a file:// origin can ever be granted persistence in real use is unknown.
- Quota behaviour at the real ceiling. 40MB was written; the full 500-photo cache the PRD implies (thumbnails + 1600px previews + HEIC sidecars) was not, so eviction behaviour under storage pressure — and how it interacts with the shared file__0 bucket — is untested.
- IndexedDB behaviour when two file:// tools collide in the shared file__0 bucket (name clashes, version conflicts, quota starvation) was observed structurally but not stress-tested.
